## Value

one request builds several entries at once. P15 lets you run parallel
sessions, but you still pick the entries, start each session, and keep track of
them. Here you say "handle the next 3", and one orchestrating session does the
picking, the dispatching, and the relaying of questions. P15's machinery does all
the git work.

## Scope

- Pick: the next N entries from `docs/backlog/QUEUE.md` that are
  dependency-ready. Skip any that depends on an unshipped entry, including one picked
  in the same batch; P23's graph decides this. Overlap is not a reason to skip: a
  collision costs a rebase and a resolution at landing (P15), not a broken main. Say
  what was picked and what was skipped, and why.
- Dispatch: one plain background subagent per picked entry, running `/implement`
  with the `cd` way of working its worktree (A-12). Claims and landings go through
  P15's lock. The orchestrator itself runs no git.
- Questions: a subagent at a gate that needs the owner (a rescope, a milestone
  choice, a stale premise, `land.mjs` exit 4) stops and returns its question. The
  orchestrator asks the owner, naming the entry, and resumes that subagent with the
  answer (SendMessage). The others keep working meanwhile. A question raised while
  that subagent holds the land lock goes first, and the orchestrator says so: every
  other landing waits on it.
- Collect: each entry's landing report, then one "ship it?" per entry.
- Out: auto-shipping (acceptance stays yours); picking from outside the queue;
  predicting file overlap.

## Accept

- I say "handle the next 3" once. It names the entries it picked, and any it
  skipped with the reason, then starts one subagent per entry.
- When a subagent needs me, I get its question from the orchestrator, naming the
  entry. My answer gets that subagent going again, and the others keep working
  meanwhile.
- I type no git command from start to finish. Each entry lands on main through
  P15's flow and comes back with its per-criterion report.
- None is flipped `shipped` without my word.

## Notes

Rescoped 2026-10-19 on the product owner's word. The first scope rested on
two assumptions, both refuted the same day:

- A-8: a build's footprint can't be predicted from its entry. 9 of 19 pairs
  predicted not to overlap did share a file.
- A-12: a subagent can't use EnterWorktree/ExitWorktree. The P26/P27 drill showed
  plain subagents can run P15's flow by `cd`, which `/implement` now documents.

here, so the build should probe it first. If subagents are handed /implement as
pasted text rather than invoking it, A-4 applies to them too.
