## Value

the queue's order is a claim ("this is what to build next") that today rests
on whichever session last wrote it. Generated from the graph, the order is the same
whoever runs it, and a hand edit that breaks it fails the check.

## Scope

- A generator (a new `queue` npm script) rewrites `docs/backlog/QUEUE.md` from P23's graph. It picks
  greedily: of the candidates (every `P#` dependency shipped or already picked, every
  `A-n` dependency settled), the one that unblocks the most open entries goes next,
  counted transitively. At most five items.
- Tie-break: entries already in the queue keep their current order, read from the
  file being replaced; newcomers follow, lowest ID first.
- Each item's why is generated: the entry's title and what it unblocks.
- The schema check fails when QUEUE.md is not what the generator would write from it.
- /ship's queue refresh becomes "run the generator"; the backlog README's ranking
  rule points at the generator instead of describing it.
- Out: hand-written notes on queue items (the queue holds generated lines only).

## Accept

- The generator puts entries that unblock more open entries first, and every
  item's why names what it unblocks.
- Tied entries keep their order from the current queue file; a new entry ties in
  behind them, lowest ID first.
- Reordering QUEUE.md by hand, or leaving out a ready entry that outranks a queued
  one, fails the check and names both IDs.
- Running the generator twice in a row changes nothing.

## Notes

user decision 2026-10-16: ranking is computed, not judged, with the
existing-order tie-break coded in. Reading the tie-break from the file being
replaced, rather than from git, avoids shallow-clone trouble (see P20's notes).

Re-read 2026-10-19 after P23 shipped; the premises hold. P23's graph is
`dependencyGraph` in scripts/entries.mjs and gives forward edges only (what an entry
waits on). Counting what an entry unblocks needs the reverse walk, which the
checker's `--graph` view already does for its "unblocks N" line.
