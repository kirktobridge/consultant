## Value

the big builds get a plan I approve before any code is written, decided
when the entry is filed rather than left to the building session's judgement in
the moment. Today that's one prose line in /implement ("for anything nontrivial").

## Scope

- A `plan: yes | no` header field on every open product entry, set by /triage when
  drafting and changed only by rescoping through /ship. The one-line reason goes in
  the body as `Plan: yes|no — reason` under Notes (the form P24 and P39 already use).
- /implement: an entry marked yes gets a written plan (files to touch, order, risks),
  after the premise gate and before the first code edit, and waits for approval.
  Under /orchestrate the plan goes back as a `QUESTION <ID>:` hand-back, which the
  orchestrator relays like any other question. Marked no keeps today's rule: plan
  anyway if the build turns out nontrivial.
- The schema check requires the field on open product entries, and the backlog
  README documents it, in the same commit (checker, README, and entries.mjs move
  together). Existing open entries get the field in that commit. Where Notes already
  say `Plan: yes|no`, that line is the value.
- Out: bugs (a fix is contracted by its Repro, and today's rule covers it); sizing or
  effort estimates (A-5); storing a plan anywhere beyond the conversation and the
  build commit.

## Accept

- Every new triage draft says whether the entry needs a plan, with a reason; an open
  entry without the field fails the schema check.
- Implementing an entry marked as needing a plan stops for my approval of a written
  plan before any code changes.
- An entry marked as not needing one still gets a plan when its build turns out
  bigger than drafted — the mark is a floor, not a ceiling.
