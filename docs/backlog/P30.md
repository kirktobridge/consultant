## Value

/implement's DEPENDS GATE still says a milestone "explicitly marked unblocked" may be
built past an unmet dependency, but the schema check refuses that claim regardless:
`depends_on` can't say which milestone needs what. The instruction is now false, and
following it ends in a failed claim commit. One route instead: a milestone that can go
ahead without a dependency is promoted to its own entry, with its own `depends_on:`.

## Scope

- /implement's DEPENDS GATE loses the "explicitly marked unblocked" exception. In its
  place: if a milestone can go ahead without the blocking dependency, stop and propose
  promoting it to its own P# via /triage → /ship. The new entry carries only its own
  dependencies, and the parent depends on it when it builds on that piece.
- The backlog README (via /ship, at land) says the same where it describes milestones.
- An /eval case: asked to build R0 of an entry that depends on an unshipped P#, whose
  Scope says R0 doesn't need it, /implement refuses, names the dependency, and proposes
  the promotion.
- Out: per-milestone `depends_on` (rejected 2026-10-19).

## Accept

- Asked to build a milestone whose entry depends on an unshipped `P#`, /implement
  refuses and names the dependency, even when the Scope says that milestone doesn't
  need it.
- That refusal proposes promoting the milestone to its own entry and says the parent
  may depend on it.
- The /implement skill text and the backlog README no longer describe any way to
  build past an unmet dependency.

## Notes

Surfaced by P23's build (f31092f). User decision 2026-10-19: drop the exception
rather than give milestones their own `depends_on`. A milestone that can go ahead
without a dependency is promoted to its own P#, and its parent depends on it where
appropriate. The schema check's claim gate already enforces the rule
(mechanically enforced since P23). This entry fixes the instructions that contradict it.

Plan: yes — it changes /implement's dependency gate and the backlog README, and adds an eval case.
