## Value

The owner hears about a security review only when it found something. A clean one
stays in git, where it can be checked, instead of in what they have to read.

## Scope

- scripts/review.mjs prints the exact review line for the owner's report: the
  /code-review outcome, and the /security-review outcome only when it found
  something. When security was clean, that half is left out. The commit's `review:`
  line keeps recording both.
- /implement's close step reports that line as printed and says nothing more about
  a clean security review. /land and /orchestrate relay it as is.
- Out: a hook that rewrites the final message (option 4, turned down: brittle). An
  eval case (option 3) is a later entry if drift shows up.

## Accept

- After a build whose /security-review found nothing, the close report and /land's
  handshake don't mention the security review.
- After one that found something, the findings are reported as before.
- The commit message still records that the security review ran and what it found.

## Notes

The owner asked for this on 2026-10-21 ("If security review doesn't find anything
notable, I don't really want to hear about it") and chose options 1 + 2: a rule in
/implement's close step, with review.mjs printing the line so code decides it. It is
held in session memory until this ships; delete that memory entry
(quiet-clean-security-review) when it does.
