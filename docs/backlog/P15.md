## Value

you never manage the git tree. Today you choose when to take a worktree,
when to /land, and what to clean up, and running sessions in parallel depends on you
following the GUIDE's rules by hand. Those rules become things the loop does.

## Scope

- R1 — `/implement P#` provisions its own worktree + `feat/p<#>-<slug>` branch off
  local main, after the claim commit, and the session works there. The rule that
  makes this allowed goes in CLAUDE.md: EnterWorktree acts only on user or
  CLAUDE.md/memory instructions, and a SKILL.md isn't on that list. settings.json
  sets `worktree.baseRef: head` (A-6). `.claude/worktrees/` is gitignored, so the
  main checkout stays clean.
- R2 — when /implement closes green, it runs /land itself. Claims and landings take
  one repo-wide lock, so two sessions that finish together land one
  after the other instead of colliding. The lock is a file in the git common dir,
  taken from inside the worktree and held until the merge is done. Under it, the
  session rebases its branch onto local main *in its worktree*, resolves any
  conflict there, re-runs the suite, and only then exits to the main checkout and
  merges. Main never holds a conflicted merge. The lock records pid and timestamp so
  a stale one can be told apart. This replaces /land's "never auto-resolve" rule,
  with these guards:
  - Before resolving, the session reads the other entry's merge commit and backlog
    file, so it resolves knowing what both sides meant, not only its own entry.
  - A check flags any line the newly landed merge added that the rebased branch
    deletes. That's the "resolved by reverting the other session" failure, and the
    suite can't catch it in skill prose.
  - It stops for the user only if the suite is red after resolving or that check
    fires. Otherwise it lands and reports each conflict: file, both sides, the
    resolution and why.
  - After a non-trivial resolution, the close report's verdicts no longer describe
    the code. Either /verify re-runs, or the acceptance handshake marks each verdict
    *observed before conflict resolution*.
- R3 — once a branch lands, its worktree and branch are removed. The session-start
  audit (`scripts/session-audit.mjs`) gains a check that flags any worktree whose
  branch is merged or whose claim is gone, and any land lock whose pid is dead.
- Out: remotes, PRs and merge queues; auto-*shipping*. Landing stays separate from
  acceptance, and `shipped` still waits for you.

## Accept

- From `/implement P#` until it has landed on main, I type no git command and answer
  no git question, unless resolving a conflict leaves the suite red or undoes the
  other entry's work.
- Two sessions started at once on two different entries each get their own branch
  and worktree, and both end up merged on main.
- Two sessions finishing at the same moment land one after the other: main shows
  both merges, and the suite is green after each.
- Once an entry has landed, `git worktree list` no longer shows its worktree, and
  its branch is gone.

## Notes

The claim and the landing happen after the session leaves its worktree
for the main checkout (ExitWorktree `keep`), under the lock: an EnterWorktree-isolated
session is refused git commands aimed at another checkout (`git -C <main>`), and
some `rtk`-rewritten git commands (*observed* during the A-6/A-7 probes,
2026-10-15). The main checkout becomes integration-only; hand-edit it while sessions
run and landings stop at the clean-tree check. P12 doesn't block this, but if it
lands first, the lock and claim helpers use its trunk command rather than `main`.
Re-read 2026-10-16 after P16 shipped: P16 settled the dependency and moved nothing
else described here. Re-read 2026-10-16 after P18 landed: with HANDOFF and
/checkpoint gone, R2's lock covers claims and landings only, and R3's check goes in
the session-start audit, which has no worktree check yet (*verified* by
grep-checked).
Rescoped 2026-10-19: R2 resolves in the worktree, before the merge. Two parts of
that are *asserted*, not probed: that a worktree-isolated session may write a lock
file in the git common dir, and may `git rebase` onto local main (a ref shared
across worktrees). The A-6/A-7 refusals were for commands aimed at another
checkout, and these aim at the session's own. R1's build should check both first.
