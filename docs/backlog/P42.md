## Value

all five groom groups can be decided from the docs and git, but a session derives each
one by hand, so a missed dependent is silent. The session audit, /ship's sweep and
/triage groom each answer "what did this resolution unblock" separately.

## Scope

- One shared function answers what a resolution unblocked or voided. Session-audit
  section 4 (as P25 leaves it), groom.mjs and /ship step 3 all use it.
- In: the shared function also answers for a `superseded` decision (its dependents
  re-point to `superseded_by:`; nothing is unblocked), reads bugs' `depends_on:` as
  well as features', and counts a resolution as recent by its own file's change, not
  by any change in its register's folder.
- `scripts/groom.mjs` prints the five groups (unblocked, newly void, about to
  block, stale, abandoned), each item with its suggested action. Read-only; exit codes
  as the audit's. About to block = an open A-n or D-n whose dependents are queued
  (the recorded order joins with P24; see Notes).
- /triage groom starts from its output. The judgement steps (still accurate / rescope
  / void, the spike decision) stay prose.
- Out: applying any change.

## Accept

- With an assumption verified after an entry was drafted, groom lists the entry as
  unblocked; with it refuted, as possibly void, including any shipped dependent.
- An open assumption blocking the queue's head appears under "about to block"; one
  blocking only parked entries doesn't.
- For the same repo state, the audit's section 4 and groom name the same dependents
  for a resolution, bugs included; a superseded decision is worded as a re-point to its
  `superseded_by:`, and an edit to one settled entry's file re-raises only that entry.
- A groom run leaves `git status` unchanged.
