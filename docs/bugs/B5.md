## Repro

Found by /code-review on B4's diff, in the check scripts/landing.mjs carries (moved
there from status.mjs; status.mjs and next.mjs both read it):

1. P1 has two `feat/p1-` branches: an earlier milestone's, still holding commits it
   never merged, and the current one, which has landed. The ancestry check looks at
   whichever branch sorts first, so P1 reads as being built.
2. P1 lands and /land deletes its branch. The owner rejects it, so it stays
   `in-progress` with no new claim commit, and `worktree.mjs start P1` makes a fresh
   branch at main's tip. That branch is an ancestor of main, so P1 still reads as
   landed while it is being rebuilt.
3. A branch merged through GitHub (`Merge pull request #12 from kirk/feat/p1-thing`)
   is not recognized as a landing.

## Expected

Each case reads right: (1) landed, (2) being built, (3) landed.

Fix landed 2026-10-21 (merge 37b1624): scripts/landing.mjs checks every `feat/<id>-`
branch, treats one cut after the claim and not yet in a landing as a build in flight,
and reads GitHub and remote-tracking merge subjects as landings. A squash or rebase
merge is still not seen as a landing. Fixed 2026-10-21 on the user's word: all three
cases observed by /verify; accepted knowing squash/rebase merges and a branch
fast-forwarded to main with no new work still read as not landed.
